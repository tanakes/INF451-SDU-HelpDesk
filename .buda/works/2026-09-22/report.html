1. Project Overview

The SDU AI University Help Desk & Virtual Assistant is a conversational agent that helps students access academic information without navigating multiple university portals. In Sprint 1 the team delivered the foundational messaging channel and the first structured information-retrieval feature: a Telegram bot channel (US-01) and an interactive 4-topic FAQ menu with quick keyword triggers (US-02).

2. Software Architecture

The system is built entirely on the Buda.im agentic platform, which removes the need for a custom backend server, webhook host, or reverse proxy. The architecture has four layers:

2.1 Core Runtime — Buda.im Agent Sandbox

Cloud-based, stateful agent runtime
  • The AI agent executes inside an isolated cloud sandbox provided by Buda.
  • Persistent Drive storage (/agent) survives sandbox restarts and stores configuration, knowledge files, and session logs.
  • A persistent Session Memory Engine tracks multi-turn conversation context per user.

2.2 Messaging Layer — Native Telegram Channel Gateway

Serverless message dispatch (US-01, Constraint 1)
  • The bot is connected to Telegram using Buda's built-in Telegram Channel connector, authenticated with an official @BotFather API token entered directly into Buda Space Settings → Chat Channels.
  • Buda's cloud gateway manages webhook ingestion, message routing, and rate limiting — no VPS, Nginx reverse proxy, or SSL certificate maintenance is required.
  • Each Telegram chat_id is mapped 1-to-1 to an isolated session on persistent storage, keeping every student's conversation history separate.

2.3 Application / Persona Layer — SOUL.md

Behavior, tone, and output-formatting rules
  • SOUL.md defines the assistant's identity, scope (Sprint 1: US-01 & US-02 only), and tone.
  • Enforces silent execution — no internal reasoning or tool-call narration is ever shown to the student.
  • Enforces Telegram-safe output formatting: no raw Markdown headings (#), no broken nested asterisks, unicode bullets instead.
  • Defines the keyword-matching contract used by US-02 (case-insensitive, punctuation-tolerant).

2.4 Knowledge / Data Layer — faq.json

Decoupled Single Source of Truth (US-02, Constraint 2)
  • All verified SDU facts and their quick-trigger keyword arrays live in /agent/sdu-helpdesk-bot/faq.json, fully decoupled from the prompt code.
  • Updating a topic's facts or its keyword list changes the bot's behavior immediately — no redeployment needed.

2.5 High-Level Data Flow

Student (Telegram app) │ text message ▼ Buda Telegram Channel Gateway (BotFather token auth, webhook, rate-limit) │ routed message + chat_id ▼ Agent Workspace (session lookup / creation by chat_id) │ reads persona rules ▼ SOUL.md (behavior + Telegram-safe formatting + keyword-match contract) │ looks up topic / keyword ▼ faq.json (Single Source of Truth: 4 topics, keywords, summaries, FAQ entries) │ formatted answer ▼ Buda Telegram Channel Gateway → Student's Telegram chat

3. UI / UX Design

The interface is entirely conversational — there is no separate custom UI to build; the "interface" is the native Telegram chat client, kept clean and predictable through response-formatting rules defined in SOUL.md.

3.1 Interaction Model

  • Greeting / menu trigger: sending hi, hello, start, or menu presents the 4-topic quick menu.
  • Numbered or keyword shortcuts: a student can reply with a digit (1–4) or a keyword (e.g. tuition, dorm) to jump directly to a topic.
  • Free-form questions: a student can also type a specific question in natural English; the bot matches it to the closest FAQ entry rather than dumping the full topic summary.
  • Fallback: unrecognized input never returns an unrelated topic — the bot responds with a polite notice and re-displays the 4-topic menu.

3.2 Formatting Rules Applied to Every Reply

RuleReason
No # / ## Markdown headingsTelegram renders hash symbols as literal text, not headings.
Unicode bullets (•) instead of nested asterisks (* **)Nested Markdown asterisks render as broken syntax on Telegram clients.
No raw URLs / clickable linksDirect link dispatch is deferred to Sprint 2 (US-04); office/platform names are used instead.
Single blank line between sectionsReadability on small mobile screens.
English-only responsesSprint 1 scope; non-English input receives a polite English notice with the menu.

3.3 The 4-Topic Menu (US-02 core UX artifact)

🎓 Welcome to SDU University Help Desk!
I am here to help you with our frequent academic inquiries and campus services.

📌 Quick Topic Menu:
💳 1. Tuition Fees — payment deadlines, ECTS credits, Kaspi payment
📝 2. Course Add/Drop — registration portals, dates, ECTS limits
🏢 3. Dormitory — Student House facilities, required documents, schedule
📄 4. Transcripts — requesting official transcripts

Type a number (1-4) or a keyword (e.g., 'tuition', 'dorm') to get information.

3.4 Privacy-by-Design UX

The assistant never asks for or logs passwords, IIN, or bank card details — sensitive-credential prompts are excluded from the conversation flow entirely.

4. Database & Data Structure

Sprint 1 does not use a relational database. Persistence is handled through two file-based stores on Buda's persistent Agent Drive: a structured JSON knowledge base and per-user session logs.

4.1 Knowledge Base — faq.json

Single Source of Truth for all four Sprint 1 topics. Structure (per topic object):

{ "topics": { "<topic_key>": { "title": "string", // e.g. "Tuition Fees" "number": "integer", // menu shortcut number (1-4) "keywords": ["array of strings"], // case-insensitive trigger matches "source_url": "string", // verified sdu.edu.kz source "summary": "string", // topic overview shown on shortcut match "faq": [ { "question": "string", "answer": "string" } ] } } }

Four topic keys are defined: tuition, registration, dormitory, transcripts — matching the menu items Tuition Fees, Course Add/Drop, Dormitory, and Transcripts.

4.2 Session Storage — Agent Drive

  • Each Telegram chat_id is mapped to its own session file/folder on the persistent Agent Drive.
  • Session files store conversation turns, enabling multi-turn context (US-01 responsibility 3 / Scenario 2).
  • No cross-session data mixing: one student's history is never exposed to another.

4.3 Data Integrity Rules

  • The bot is restricted to reading only faq.json — no fallback file scanning or recovery attempts on missing/corrupted data.
  • If faq.json is inaccessible or retrieval fails, a fixed safe-error notice is returned instead of crashing or hanging (verified in US-02-QA Scenario 6).

5. User Story US-01 — Telegram Bot Channel Integration

"As a Student, I want to interact with the university help desk via a Telegram bot, so that I can easily access academic assistance anytime from my messaging app."

Assignee: Berdikul AliEstimation 3/10Priority High (LCHV)Sprint 1

Responsibilities

  • Connect the AI Help Desk agent to Telegram using Buda's native Telegram Channel connector with BotFather API credentials.
  • Receive incoming text messages from students in Telegram, route them to the agent workspace, and return AI-generated responses back to the student's chat.
  • Maintain chat session continuity for individual Telegram user IDs across conversations.

Constraints

  • The solution must use Buda's native Telegram Channel Gateway for message dispatch rather than hosting an external server.
  • The interaction must remain entirely within the native Telegram chat interface without requiring external portal authentication for general academic inquiries.

Maintenance Tasks

  • Task (Verified): Set up and verify Telegram bot token via @BotFather and connect it to the Buda channel settings.
  • Task (Verified): Configure response formatting rules in SOUL.md to ensure messages render cleanly on Telegram.
  • Task (Verified): Confirm active channel connection status and verify message exchange in real Telegram chats.

  • Responses must render cleanly on Telegram.
